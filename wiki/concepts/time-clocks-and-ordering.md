# Time, clocks and ordering

**In one sentence.** In a distributed system "happened before" is a partial order defined by
messages, not by wall clocks — and every mechanism for ordering events either lives with that
partial order (vector clocks, causal consistency) or manufactures a total one (Lamport clocks,
consensus, TrueTime).

## Happens-before (Lamport 1978)
Events a → b if (1) same process and a precedes b, (2) a is the send and b the receive of one
message, (3) transitivity. Otherwise a ∥ b — **concurrent**, and no observer within the system
can tell which "really" came first (Lamport: the specification must be in terms of events
observable within the system). Space-time diagrams; the relation is what relativity gives
physics. Consequences: no global "now"; "the latest write" is ill-defined without an agreed
order.

## Logical clocks
- **Lamport clock**: each process keeps a counter; increment on each event; piggyback on
  messages; on receive set C = max(C, C_msg)+1. Guarantees a → b ⇒ C(a) < C(b) (not the
  converse). Total order (C, pid) lets replicas apply operations identically — the germ of
  state-machine replication and Lamport's mutual-exclusion algorithm; last-writer-wins by
  Lamport timestamp is consistent but may discard concurrent writes.
- **Vector clock** (Fidge/Mattern 1988): one counter per process; V(a) < V(b) ⇔ a → b;
  incomparable ⇔ concurrent. Detects conflicts exactly (Dynamo's version vectors, Riak
  siblings) at O(n) size; dotted version vectors, interval tree clocks for churn. **Version
  vectors** track object versions rather than events.
- Ordering guarantees for replication ([[consistency-models]]): causal consistency = deliver
  writes respecting →; **causal broadcast** via vector timestamps; **FIFO broadcast** per sender;
  **total-order (atomic) broadcast** ≡ consensus ([[consensus-paxos-raft]]).

## Physical clocks (Kleppmann lecture 3; DDIA ch. 8)
Quartz drift ~ tens of ppm (seconds per day); **NTP** hierarchy of strata, round-trip
estimation, slewing vs stepping; **PTP** with hardware timestamps for μs accuracy; GPS/atomic
references in datacenters. **Time-of-day** clocks can jump (NTP steps, leap seconds — smeared by
Google) — never measure durations with them; use **monotonic** clocks (`CLOCK_MONOTONIC`,
`Instant`). Timestamps as global ordering are unsafe (skew of ms; Cassandra LWW can drop
writes). Lamport's paper also derives the bound on clock synchrony given message delay
uncertainty. **Leases** require bounded drift; process pauses (GC, VM migration) make even a
correct clock's owner late — hence fencing tokens ([[distributed-systems-basics]]).

## Hybrid and bounded clocks
**Hybrid logical clocks** (Kulkarni 2014): (physical time, logical counter) — close to wall
time, respects causality; CockroachDB, YugabyteDB. **TrueTime** (Spanner): `TT.now()` returns
[earliest, latest] with ε ≈ 1–7 ms from GPS/atomic masters; commit at a timestamp then
**commit-wait** until latest < timestamp so that any later-starting transaction sees a larger
timestamp — external consistency without global coordination ([[distributed-databases-and-nosql]]).
AWS Time Sync/ClockBound and precision clocks make this broadly available.

## Global snapshots (Chandy & Lamport 1985)
Marker messages on FIFO channels record a **consistent cut** (no received-but-unsent messages)
while the system runs — basis for checkpointing in Flink, deadlock/termination detection,
distributed debugging.

## Pitfalls
- Sorting events by wall clock across machines; LWW on skewed clocks.
- Measuring elapsed time with time-of-day clocks; ignoring leap seconds and NTP steps.
- Assuming a lease holder is still the holder after a GC pause.
- Vector clocks sized by clients rather than replicas (unbounded growth).
