# Symbolic execution and concolic testing

**In one sentence.** Execute the program on unknowns, collect the branch conditions each
path took, and ask a solver for inputs that satisfy them — every path becomes a test
and every reachable assertion failure becomes a witness; concolic execution does it one
concrete run at a time so real programs, environments and unsolvable operations stop
being blockers.

## The idea (KLEE §1 — read; King 1976)
"Instead of running code on manually- or randomly-constructed input, they run it on
**symbolic input** initially allowed to be 'anything'. They substitute program inputs with
symbolic values and replace corresponding concrete program operations with ones that
manipulate symbolic values. When program execution branches based on a symbolic value,
the system (conceptually) follows both branches, on each path maintaining a set of
constraints called the **path condition** which must hold on execution of that path. When
a path terminates or hits a bug, a test case can be generated by solving the current path
condition for concrete values." Determinism makes the generated input replay the same
path on the unmodified program. Example: `if (x > 10) { if (y == x*2) crash(); }` — path
condition for the crash: x > 10 ∧ y = 2x; solver returns x = 11, y = 22. The solver is an
**SMT** solver over bitvectors and arrays ([[sat-and-smt-solvers]]: STP for KLEE, Z3 for
SAGE/Pex); each symbolic branch is a **feasibility query** (is PC ∧ cond satisfiable? PC ∧
¬cond?) — infeasible paths are pruned, which is what makes this more than path
enumeration. Bugs found are **implicit-oracle** bugs (crashes, memory errors — KLEE checks
every pointer dereference against the object it must lie in, division by zero, assertion
failures — [[design-by-contract]]) plus **differential** ones (cross-checking two
implementations by asserting outputs equal under symbolic input —
[[software-testing-fundamentals]]).

## KLEE (Cadar, Dunbar & Engler, OSDI 2008 — read)
Interprets **LLVM bitcode** (so C/C++ and anything else that compiles to it); each
**state** = registers, stack, heap (as a map of objects), path condition, program counter;
forking copies a state with **copy-on-write** at object granularity so thousands of states
fit in memory. **Constraint-solving optimizations** (the bulk of the time): expression
rewriting/simplification; **implied-value concretization** (x + 1 = 10 ⇒ x = 9, substitute
everywhere); **constraint independence** (split the PC into independent subsets; query
only the relevant one); a **counterexample cache** (previous solutions and unsat cores
answer sub/superset queries without the solver). **Search heuristics** interleaved
round-robin: **random-path** (walk the execution tree from the root, choosing randomly at
each fork — favours shallow states, avoids fork-bombing loops) and **coverage-optimized**
(weight states by distance to uncovered instructions and recent progress). **Environment
problem**: system calls are redirected to a ~2 500-line model — a **symbolic file system**
(files whose contents are symbolic, with symbolic sizes), symbolic stdin, symbolic
command-line arguments (`--sym-args 0 3 10`), models of `read/write/stat/…` that can also
fail symbolically (to exercise error paths). **Results**: Coreutils 6.10 (89 tools):
84.5 % total line coverage, > 90 % per tool on average (median 94 %), higher than the
developers' suite for 76 of 89; BusyBox 90.5 %; 56 bugs in 452 programs / 430 K lines
including three Coreutils bugs undetected for 15 years (e.g. `paste -d\\` , `mkdir -Z`,
`pr -e`); cross-checking 67 BusyBox vs Coreutils pairs found real inconsistencies and
functional bugs (`tee`, `comm`, `cksum` …); ran on the HiStar kernel. Lineage: EXE (2006)
→ KLEE (still maintained; used on aerospace, automotive, Coreutils CI); S2E (whole-system
on QEMU); angr (binaries, Python); Java PathFinder/SPF; Pex/IntelliTest (.NET); Manticore;
symbolic execution in `cargo-kani`/CBMC is bounded model checking ([[model-checking]]).

## Concolic execution: DART, CUTE, SAGE (Godefroid, Klarlund & Sen 2005; Godefroid et al. 2008)
**Directed Automated Random Testing**: instrument the program; run it **concretely** on a
random/seed input while a shadow symbolic state records the **path constraint** as a
sequence of branch conditions; pick the last (or a chosen) constraint, **negate** it, keep
the prefix, ask the solver for an input satisfying prefix ∧ ¬cond, run again → a new path;
depth-first over the tree (**generational search** in SAGE: negate *every* constraint of a
path, score children by coverage gain, so one run yields many new inputs). Advantages: the
environment is just executed (no models); when a constraint is beyond the solver
(non-linear, hash, floating point, external library), **concretize** — substitute the
concrete value from the run and continue (losing completeness, keeping soundness of
the generated test); scales to large binaries. **SAGE** at Microsoft: whitebox fuzzing of
file parsers (x86 instruction-level tracing, Z3), ran continuously on hundreds of machines
since 2008; "found one-third of all the bugs discovered by file fuzzing during the
development of Windows 7", bugs that blackbox fuzzers missed; costs: sessions of hours to
days, tracing overhead 10–100×. Related: CUTE/jCUTE (C/Java), CREST, Pex (parameterized
unit tests → concolic test generation), the Fuzzing Book's "Concolic Fuzzing" and
"Symbolic Fuzzing" chapters (Python, z3 — `ConcolicTracer` records constraints on
proxy-wrapped values).

## The two hard problems and how they're attacked
**Path explosion**: paths grow exponentially with sequential branches and loops (a loop
over a symbolic length is unbounded). Mitigations: search heuristics (coverage, distance,
random path), **loop bounding/unrolling limits**, **state merging** (join states at
control-flow joins into one with `ite` expressions — trades path count for constraint
complexity; veritesting), **pruning** infeasible/redundant states (path-condition
subsumption), **function summaries** (compositional SE — SMART: summarize callee behaviour
as pre/post pairs), **under-constrained** SE (start from any function, treat parameters as
unconstrained — UC-KLEE finds bugs without a harness), **chopped** SE (skip irrelevant
code), and pointing the search at targets (patches, sanitizer sites). **Environment**:
model it (KLEE), execute it concretely (concolic), or run whole-system (S2E, QEMU) —
each trades coverage of environment-dependent error paths against fidelity. Other
limits: **symbolic pointers**/memory (aliasing → array theory or concretization),
**floating point** (solvers weak; concretize), **hash functions and cryptography**
(intentionally un-invertible — fuzz or use the key), concurrency (schedules multiply
paths — see [[model-checking]] and DPOR), solver timeouts (each query can be NP-hard).

## Hybrid fuzzing: the modern division of labour (Driller 2016; QSYM 2018)
Greybox fuzzing ([[fuzzing]]) explores cheaply but gets stuck at `if (magic == 0x4D5A)`
or checksum checks; symbolic execution passes those but explores slowly. **Driller**: run
AFL; when coverage stalls, hand the stuck seeds to angr, solve for inputs that pass the
blocking branches, feed them back as seeds. **QSYM**: a fast concolic executor
(instruction-level DBI, aggressive concretization, optimistic solving — try solving only
the last constraint) tuned to be a fuzzer's helper rather than a complete SE engine —
found 13 CVEs where fuzzers plateaued. Also **SymCC**/**SymQEMU** (compile symbolic tracking
into the binary — 10–100× faster than KLEE-style interpretation), Intriguer, Pangolin.
Rule of thumb: fuzz first (hours, cheap); add solving for the branches coverage reports
show as never-flipped; use full KLEE-style SE for small, closed, security-critical units
(parsers, crypto libraries, kernel drivers) and for **equivalence checking** across
versions/implementations.

## Pitfalls
- Expecting SE to "verify": it explores paths up to a bound with a partial environment —
  absence of found bugs is bounded evidence, not proof ([[program-verification]]).
- Unbounded loops and symbolic sizes → state explosion; set bounds and targets.
- Concretization silently drops paths — read the coverage report for unflipped branches.
- Harness bugs (over-constrained inputs) → high "coverage" of nothing; under-
  constrained inputs → false positives in UC-KLEE.
- Solver as bottleneck: time limits, caching, and simplification dominate engineering.
